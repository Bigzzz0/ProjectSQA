## 1. สิ่งที่ควรรู้ก่อนเข้าห้องสอบ ("อะไรคืออะไรบ้าง")

### 1.1 MIO Algorithm (Many Independent Objective) คืออะไร?
* **MIO เป็น Search-Based Software Testing (SBST):** เป็นขั้นตอนวิธีเชิงพันธุศาสตร์ที่พัฒนาต่อยอดมาจาก Genetic Algorithm ดั้งเดิม
* **จุดเด่นที่ต่างจากวิธีเดิม:**
  1. **ตัด Crossover ทิ้ง 100% (No Crossover):** อัลกอริทึมรุ่นเก่าจะเอาโค้ดเทส 2 อันมาตัดแปะสลับบรรทัดกัน ซึ่งมักทำให้ Object พัง รันไม่ผ่าน MIO จึงใช้เฉพาะ **Mutation (การเปลี่ยนค่าตัวแปร)** และ **Insertion (การสุ่มแทรกคำสั่ง)**
  2. **Target-Centric Archive:** แยกช่องเก็บเทสตามแต่ละ Branch/Line เป้าหมายในโค้ด เทสตัวไหนเข้าใกล้เงื่อนไขไหนที่สุด จะถูกเก็บไว้ในช่องนั้น และจะถูกแทนที่ก็ต่อเมื่อมีเทสใหม่ที่เข้าใกล้กว่าหรือสั้นกว่า

### 1.2 Search Budget คืออะไร และมีผลอย่างไร?
* **นิยาม:** คือ **"เพดานเวลา"** ที่เราอนุญาตให้ EvoSuite ใช้ค้นหาและกลายพันธุ์ชุดทดสอบต่อ 1 คลาสเป้าหมาย (ในการทดลองเราตั้งไว้ 3 ระดับ: **30, 60 และ 120 วินาที**)
* **ผลของ Budget:**
  * **ยิ่งให้เวลามาก Coverage ยิ่งสูงขึ้น:** จาก 30s ได้ 65.7% $\rightarrow$ 60s ได้ 68.7% $\rightarrow$ 120s ได้ 70.8% (มีนัยสำคัญทางสถิติ $p < 10^{-67}$)
  * **ภาวะ Diminishing Returns (ความคุ้มค่า):** การเพิ่มเวลาจาก 30s เป็น 120s (เพิ่มเวลา 4 เท่า) ได้ Coverage เพิ่มขึ้นมาเพียง ~5% แต่กินเวลาเครื่องเกือบ 200 วินาทีต่อคลาส **สรุปว่า 60 วินาทีคือจุดสมดุลที่ดีที่สุด (Sweet Spot)**

### 1.3 Random Seed คืออะไร และมีผลอย่างไรกับ Budget?
* **นิยาม:** คือ **"ค่าตั้งต้นของตัวสุ่มเลขเทียม (PRNG)"** (เราทดลอง 3 Seeds: **101, 102, 103**)
* **ทำไมต้องมีหลาย Seed?:** เพราะ MIO มีการสุ่มค่าตัวแปรและการสุ่มก้าวเดิน ถ้าทดลองแค่ Seed เดียว อาจเป็นความบังเอิญ (ดวงดี/ดวงร้าย) จึงต้องรัน 3 Seeds เพื่อหาค่าเฉลี่ย
* **ความสัมพันธ์ระหว่าง Seed กับ Budget (อาจารย์ชอบถาม):**
  * **ที่ Budget ต่ำ (30s):** ผลลัพธ์จะ **แกว่งตาม Seed สูงมาก (SD กว้าง)** เพราะถ้าสุ่มก้าวแรกไปผิดทาง เวลาจะหมดก่อนแก้ตัว
  * **ที่ Budget สูง (120s):** ผลลัพธ์ของแต่ละ Seed จะ **ลู่เข้าหากัน (Converge)** เพราะอัลกอริทึมมีเวลาค้นหาและปรับตัวนานพอ ทำให้ความแปรปรวนจาก Seed ลดลงอย่างชัดเจน

### 1.4 Scaffolding Class คืออะไร และต่างจาก Test Code อย่างไร?
ทุกครั้งที่ EvoSuite สร้างเทส จะได้ไฟล์คู่กันเสมอ เช่น `Target_ESTest.java` กับ `Target_ESTest_scaffolding.java`

* **Test Code (`*_ESTest.java`):**
  * เป็นไฟล์ที่เก็บคำสั่ง `@Test` จริง ๆ มีการสร้าง Object, เรียก Method เป้าหมาย และใส่คำสั่ง Assert (`assertEquals`, `fail`) เพื่อตรวจพฤติกรรมโค้ด
* **Scaffolding Class (`*_ESTest_scaffolding.java`):**
  * เป็น **"คลาสแม่ (Target_ESTest extends Scaffolding)"** ทำหน้าที่เป็น **Sandbox & Infrastructure Harness**:
    1. **Sandbox & Security:** ป้องกันไม่ให้เทสที่สุ่มขึ้นมาไปลบไฟล์จริงในเครื่อง หรือเปิด Network Socket
    2. **JVM State Reset:** รีเซ็ตตัวแปร Static, TimeZone, System Properties ก่อนและหลังรันเทสแต่ละตัว ป้องกันไม่ให้เทสตัวก่อนหน้าทิ้งขยะไว้จนเทสถัดไปพัง (ป้องกัน Flaky Tests)
    3. **ThreadStopper:** เป็น Kill Switch ดับ Thread ทันทีหากโค้ดหลุดเข้า Infinite Loop (ตัดจบใน 3,000ms)
    4. **Deterministic Class Loading (`initializeClasses`):** บังคับโหลดคลาสทั้งหมดในสายสัมพันธ์ล่วงหน้า เพื่อให้สภาพแวดล้อมนิ่งสนิทและป้องกัน Timeout

### 1.4.1 เจาะลึกโค้ด Scaffolding: `initializeClasses()` คืออะไร และทำไมรายชื่อคลาสถึงเยอะมาก?
*(กรณีตัวอย่างจากโค้ดจริงในโปรเจกต์ เช่น [MultiplePiePlot_ESTest_scaffolding.java](file:///e:/Coding/ProjectSQA/MIO_Algorithm/TestCode/Chart_12b/MultiplePiePlot_ESTest_scaffolding.java))*

เมื่อเปิดไฟล์ Scaffolding จะพบบล็อกคำสั่งยาวหลายร้อยบรรทัดในฟังก์ชัน `initializeClasses()`:
```java
private static void initializeClasses() {
  org.evosuite.runtime.classhandling.ClassStateSupport.initializeClasses(MultiplePiePlot_ESTest_scaffolding.class.getClassLoader() ,
    "org.jfree.data.time.TimeTableXYDataset",
    "org.jfree.chart.labels.StandardPieSectionLabelGenerator",
    "org.jfree.chart.plot.ValueMarker",
    "org.jfree.data.resources.DataPackageResources",
    "org.jfree.data.time.Minute",
    "org.jfree.chart.Effect3D",
    ... (รายชื่อคลาสยาวกว่า 400-500 คลาส) ...
  );
}
```

#### 🔍 1. บล็อกคำสั่งนี้คืออะไร และทำหน้าที่อะไร?
* มันคือกระบวนการ **Eager Class Pre-loading** ของ EvoSuite ที่ทำงานในขั้นตอน `@BeforeClass` (`initEvoSuiteFramework()`)
* ตามปกติแล้ว Java Virtual Machine (JVM) จะโหลดคลาสแบบ **Lazy Loading** (คือเจอการเรียกใช้คลาสไหนตอนรัน ค่อยโหลดไบต์โค้ดคลาสนั้นเข้าหน่วยความจำ)
* แต่สำหรับการรัน Automated Unit Tests ของ EvoSuite การปล่อยให้โหลดแบบ Lazy จะทำให้เกิดผลข้างเคียง (Side Effects) หรือจังหวะการรัน Static Initializer (`<clinit>`) ที่คาดเดาไม่ได้
* คำสั่ง `ClassStateSupport.initializeClasses(...)` จึงเป็นการ **บังคับให้ ClassLoader โหลดและประมวลผลคลาสทั้งหมดให้เสร็จสิ้นก่อนเริ่มรันเทสเคสแรก** เพื่อสร้างสภาพแวดล้อมที่คงที่ 100% (Deterministic Environment)

#### ❓ 2. ทำไมรายชื่อคลาสถึงยาวเหยียดเป็นร้อย ๆ คลาส? ("ทำไมมันเยอะจังเลย?")
สาเหตุหลักมาจาก 2 ปัจจัยร่วมกัน:
1. **Transitive Dependency Closure (สายใยความสัมพันธ์ใน Java OOP):**
   * แม้เราจะทดสอบแค่คลาสเดียว (เช่น `MultiplePiePlot`) แต่ในเชิง Object-Oriented คลาสนี้ไม่ได้อยู่อย่างโดดเดี่ยว:
     * มันสืบทอดจาก `Plot` ซึ่งสืบทอดมาจากคลาสแม่ใน Java
     * มันเรียกใช้ Dataset ต่าง ๆ (`CategoryDataset`, `TableXYDataset`, `JDBCXYDataset`)
     * มันผูกกับ Renderers, Marker, Axis (`AxisCollection`), Label Generator, UI Contributor และ Event Listeners
     * และคลาสเหล่านั้นก็เรียกคลาสอื่น ๆ ต่อไปอีกเป็นทอด ๆ (Transitive Dependencies)
   * EvoSuite จะทำการวิเคราะห์ Bytecode Hierarchy และดึงสายสัมพันธ์ทั้งหมดที่คลาสเป้าหมายสามารถแตะต้องได้เข้ามารวมในลิสต์นี้
2. **MIO Algorithm เจาะ Branch Coverage ลึกและหลากหลาย:**
   * MIO พยายามกลายพันธุ์และสร้าง Input เพื่อทะลุผ่านเงื่อนไขทุก Branch ส่งผลให้ชุดเทสสร้าง Instance ของคลาสรูปธรรม (Concrete Classes) หลากหลายรูปแบบ เช่น ลองส่ง Dataset ชนิดต่าง ๆ ส่ง Renderer ชนิดต่าง ๆ เข้าไปในกราฟ
   * ทำให้จำนวนคลาสที่ชุดทดสอบเข้าไปสัมผัสจริงมีจำนวนมหาศาล (ในกรณีของ `MultiplePiePlot` มีมากกว่า 450 คลาส)

#### 🛡️ 3. ประโยชน์สำคัญ 3 ข้อที่ต้องทำแบบนี้ (จุดที่นำไปตอบอาจารย์):
1. **ป้องกัน False Timeout จาก `ThreadStopper` (3,000ms):**
   * EvoSuite ตั้ง Kill Switch ดับเทสที่รันเกิน 3 วินาทีเพื่อกัน Infinite Loop
   * หากปล่อยให้คลาสขนาดใหญ่ไปโหลดแบบ Lazy กลางเทสเคส เวลาที่เสียไปกับการอ่าน Disk/Classpath และรัน Static Block อาจทำให้เทสหมดเวลา (Timeout) จนเทส FAIL ทั้งที่โค้ดไม่ได้มีบั๊ก
2. **ทำให้ผลการทดสอบคงที่และทำซ้ำได้ (Deterministic & Reproducible):**
   * กำจัดความแปรปรวนจากจังหวะการโหลดคลาสของ JVM ทำให้เทสทุกตัวรันบน State ที่ถูกเตรียมพร้อมไว้เท่ากันทุกครั้ง
3. **ทำงานคู่กับ `resetClasses()` เพื่อกำจัด Flaky Tests:**
   * สังเกตว่าที่ท้ายไฟล์ Scaffolding จะมีฟังก์ชัน `resetClasses()` ควบคู่กันเสมอ
   * การที่ EvoSuite รู้จักรายชื่อคลาสทั้งหมดตั้งแต่ต้น ทำให้เมื่อรันเทสแต่ละข้อจบ (`@After doneWithTestCase()`) ระบบสามารถสั่งกวาดล้างและรีเซ็ตค่าตัวแปร Static ของทุกคลาสเหล่านั้นกลับเป็นค่าเริ่มต้น ป้องกันไม่ให้ State ตกค้างไปทำลายเทสข้อถัดไป (Zero Cross-Test Pollution)

### 1.5 เวอร์ชัน Buggy (`*b`) กับ เวอร์ชัน Fixed (`*f`) คืออะไร?
* **Buggy (`*b`):** โค้ดต้นฉบับที่มีบั๊กอยู่จริงในประวัติศาสตร์ (เช่น `Chart-1b`, `Jsoup-45b`)
* **Fixed (`*f`):** โค้ดที่ผู้พัฒนาได้ทำการแก้ไขบั๊กตัวนั้นเสร็จสมบูรณ์แล้ว
* **การตรวจจับบั๊ก (`BUG_DETECTED`):**
  $$\text{BUG\_DETECTED} \iff \text{รันบน Buggy แล้ว FAIL } \land \text{รันบน Fixed แล้ว PASS}$$
  * ถ้าเทสรันบน Buggy ก็ FAIL แล้วพอมารันบน Fixed ก็ยัง FAIL อยู่ดี $\rightarrow$ จะถือว่าเป็น **`FLAKY_OR_REGRESSION`** (เทสเขียนผิดเอง ไม่นับว่าเจอบั๊ก)

### 1.6 ทำไม Coverage สูง (63.85%) แต่ตรวจพบบั๊กได้แค่ 5 ตัว (0.60%)?
* **เพราะปัญหา "Weak Oracle" (Assertion อัตโนมัติ):**
  * **Coverage:** วัดแค่ว่าชุดเทส "วิ่งผ่านบรรทัดและกิ่งเงื่อนไขหรือไม่" ซึ่ง MIO เก่งมากในการหา Input ทะลุเข้าไปถึงโค้ด
  * **Fault Detection:** ต้องมี "Assertion ที่ตรวจสอบค่าผิดพลาดตรงจุดเกิดบั๊กจริง"
  * เนื่องจาก EvoSuite สร้างเทสแบบ Black-box/White-box โดยไม่รู้เจตนาของมนุษย์ คำสั่ง Assert ที่สังเคราะห์ขึ้นจึงมักตรวจแค่สถานะทั่วไปหรือดัก Exception พื้นฐาน ทำให้โค้ดวิ่งผ่านจุดที่มีบั๊ก แต่เทสไม่ได้จับผิดค่านั้นออกมา

### 1.7 ทำไมบั๊ก 5 ตัวของ MIO ถึงมีนัยสำคัญสูงมาก? (จุดขายหลักของ Member 2)

## 4. แนวทางการตอบคำถามอาจารย์ (Defense Q&A)

### Q1: ทำไม MIO ถึงทำ Coverage ได้สูง (63.8%) แต่ตรวจพบบั๊กได้แค่ 5 ตัว (FDR 0.6%)?

### Q6: เปิดโค้ด Scaffolding มาเจอ `initializeClasses()` มีรายชื่อคลาสยาวเป็นร้อย ๆ บรรทัด มันคืออะไร และทำไมถึงเยอะขนาดนั้น?
> **แนวคำตอบ:**  
> *"บล็อก `initializeClasses()` คือกลไก **Eager Class Pre-loading** ของ EvoSuite ครับอาจารย์
> 
> สาเหตุที่รายชื่อคลาสยาวเป็นร้อย ๆ คลาส (เช่นใน `MultiplePiePlot` มีถึง 450+ คลาส) เป็นเพราะ:
> 1. **Transitive Dependency Closure:** ใน Java OOP คลาสที่เราทดสอบมีการเรียกใช้คลาสอื่นเป็นสายใย ทั้ง Dataset, Renderer, Axis, Events และ Utility ยิ่ง MIO สำรวจ Branch Coverage หลากหลายรูปแบบ ก็ยิ่งสร้าง Object และแตะต้องคลาสในระบบมากขึ้น
> 2. **ป้องกัน Flaky Timeout:** EvoSuite มีตัวจับเวลาตัดเทสค้าง (`ThreadStopper`) ที่ 3 วินาที การบังคับโหลดคลาสทั้งหมดล่วงหน้าใน `@BeforeClass` จะช่วยไม่ให้เสียเวลาโหลดคลาสกลางเทสเคสจนติด Timeout
> 3. **ทำงานคู่กับ `resetClasses()`:** เพื่อให้ EvoSuite รู้จักคลาสทั้งหมดและสามารถตามไปรีเซ็ตตัวแปร Static ทุกตัวหลังรันแต่ละเทสเสร็จ ป้องกันผลข้างเคียงตกค้างข้ามเทสเคส (Cross-test Interference) อย่างสมบูรณ์ครับ"*
